# Cosign Agent API

`openapi.yaml` (OpenAPI 3.1, v1.0.0) describes the API that AI agents call. It matches the running code: every response was checked against its schemas on Oct 10 2026. APIMatic generates the SDKs and the docs portal from it.

Owners do not use a REST API: the Cosign web app talks to the server through Next.js server actions. The earlier draft that also described owner endpoints is kept in `drafts/` for reference.

## The agent's whole job: three calls

1. `POST /api/v1/agent/token` - swap the API key (HTTP Basic) for a 15-minute token.
2. `GET /api/v1/agent/me` - remaining budget, limits, and the stores it can pay right now (with their websites).
3. `POST /api/v1/agent/spend-requests` (with an `Idempotency-Key`) - ask to pay. The answer:
   - `COMPLETED` - paid through PayPal inside the request, receipt returned.
   - `PENDING_APPROVAL` - poll `GET /api/v1/agent/spend-requests/{id}` until the owner decides.
   - `DENIED` - reasons returned, nothing charged.

MCP clients use `POST /api/mcp` with the API key as a bearer token; its four tools mirror these calls.

## How it maps to PayPal (budget hold)

| Cosign | PayPal |
|---|---|
| Owner co-signs a slip | One `intent: AUTHORIZE` order per allowed store, `payee.merchant_id` = the store, amount = that store's share of the period budget. The owner approves each at PayPal (guided, one store at a time: PayPal allows one purchase unit per AUTHORIZE order) |
| Owner returns from PayPal | `POST /v2/checkout/orders/{id}/authorize` |
| Spend request allowed, or approved by the owner | `POST /v2/payments/authorizations/{id}/capture` inside the request, `final_capture: false`, PayPal-Request-Id derived from the spend request ID, so a retry never charges twice |
| Revoke the agent, end the slip, slip expiry, period end | `POST /v2/payments/authorizations/{id}/void` with the store's PayPal-Auth-Assertion |
| Renew (one tap before the period ends) | New AUTHORIZE order per store for the next period. At the period end the slip moves to the new holds and the old ones are voided; with no renewal the slip expires and all holds are voided. A daily job (`POST /api/jobs/daily`, secret-protected) does the switch and emails a reminder 3 days before |

PayPal IDs never appear in the API. Agents see Cosign IDs and a receipt ID only.

All these PayPal calls go through PayPal's official TypeScript Server SDK (`@paypal/paypal-server-sdk` 2.5.0, generated by APIMatic), written with APIMatic's Context Plugin for PayPal Server SDKs loaded in Claude Code. The SDK client is fixed to the Sandbox environment, has a 20-second timeout (the SDK default is none), no automatic retries, and a token provider that never rejects (the SDK caches a rejected token fetch for the life of the client). An HTTP error from PayPal is a definite refusal; a timeout or network failure is treated as an unknown outcome and retried later with the same `PayPal-Request-Id`.

**Reauthorization.** PayPal honors captures reliably only in the 3 days after an authorization. Once a hold is past that, Cosign reauthorizes it before the next capture (and the daily job renews due holds ahead of time). PayPal returns a new authorization ID with the same 29-day expiry: captures go to the newest ID, voids keep naming the original (PayPal refuses to void a reauthorized ID). Each spend request is pinned to the authorization of its first capture attempt, so a retry after a reauthorization can never become a second charge, and a PayPal "duplicate" answer is treated as "maybe charged", never as a refusal.

**Not built yet:** PayPal webhooks (to reconcile captures after the fact).

## Design decisions

- **Rules engine first, AI second.** The outcome comes from plain code. The AI purchase check runs only when the rules allow, and can only escalate to the owner (`intent_check.escalated`).
- **Integer cents everywhere**, `USD` only. The server recomputes the total from the line items and denies a mismatch (`TOTAL_MISMATCH`).
- **Idempotency-Key required** on spend requests (16-64 of `A-Z a-z 0-9 _ -`). Same key and body returns the original result; same key, different body returns `409`.
- **Approvals bind to the cart.** The owner approves the exact cart hash and total; if anything changed, nothing is charged.
- **404, not 403,** for another agent's spend request, so IDs cannot be probed.
- **Keys shown once, stored as a SHA-256 hash**, compared in constant time. Tokens are HMAC-signed and re-checked against the database on every call, so pause and revoke apply at once.
- **The agent's `purpose` is data, not instructions.** It feeds the AI check and the owner's view, never the rules.
- **Cosign never fetches `product_url`.** It is stored and shown to the owner only.
- **Budget periods of 1 to 28 days**, so a period fits inside one 29-day PayPal hold. Budgets are split per store; the rules engine also enforces the overall budget.
